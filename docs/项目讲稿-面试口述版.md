# 项目讲稿：面试口述版

用法：面试前反复练到能自然说出来，不要背稿
注意：文中数字都是 2026-10-07 真实跑出来的（模型 deepseek-chat，60 条评测集），
可以直接用；但你要能解释每一个数字是怎么测的，否则不要讲。

---

## 零、讲之前先想清楚一件事

现在几乎每个候选人的简历上都有 Agent 项目。面试官听到「我做了一个 Agent」时的第一反应是「又一个」。所以你开口的前 15 秒，必须让他知道你和别人的区别在哪。

你的区别不是"我用了 LangGraph"，而是：我做的是能真正执行的 Agent，不是只会聊天回答的；以及我认真解决了"怎么证明它算对了"这个问题。

这两句话要在开场就出现。

---

## 一、30 秒版（电梯陈述）

（以下为口述文本，请用自己的话练，不要背）

我做的是一个数据分析 Agent，解决的是这样一件事。

大模型能帮我写 SQL，但它看不到我的真实表结构，写出来的代码经常跑不通；就算跑通了，也得我自己复制到环境里执行，报错了再贴回去让它改，来回几轮省下的时间很有限。

所以我把它做成了一个能真的连数据库、自己执行、报错自己修正、最后给出结论的 Agent。

但做到这一步我发现一个更关键的问题：数据分析算错比不回答更危险。如果它算错一个指标，而这个结论被写进报告，后果很严重。所以我同时建了一套评测体系，用结果集精确比对来证明它到底算得对不对。

**这段的作用**：前 10 秒交代清楚"是什么、为什么"，后 10 秒抛出差异化（评测），最后留一个钩子让面试官往你准备好的方向问。

---

## 二、2 分钟版（标准回答，最常用）

**【开场，10 秒】**

这个项目的出发点是我做课程项目和科研时的一个真实麻烦。

**【背景，20 秒】**

我需要反复做同类数据分析，每次流程都差不多：先确认字段含义和统计口径，再写查询，然后调试报错，最后画图整理结论。一次要花 40 分钟左右，其中真正花在分析上的时间很少，大部分消耗在机械的重复劳动上——光调试 SQL 报错就要花十几分钟。而且下次做类似分析时，前面 30 分钟基本要重来一遍。

**【现有方案为什么不行，20 秒】**

我先试过通用的大模型助手，但有三个问题绕不过去：它看不到我的真实表结构，写出来的 SQL 经常跑不通；代码要我自己复制到环境里跑、报错了再贴回去改；它也没法访问数据，所以所有验证都要我自己做。后来我也试过把字段说明接进 RAG 问答，但这只解决了"字段是什么意思"，没解决执行。

**【我做了什么，25 秒】**

所以我做的是一个完整的执行链路：模型连数据库、自己生成查询、自己执行、根据报错自己修正，最后给出结论，关键数字都标注来源。核心是三个设计——语义层、SQL 安全防护、和自修正循环。

**【三个关键设计，40 秒】**

语义层是第一个。我一开始直接把 DDL 喂给模型，发现它知道字段叫 pay_time，但不知道"统计销售额必须用支付时间而不是创建时间"，经常用错字段。所以我做了一层语义定义，把字段含义、统计口径、枚举值、业务规则都写进去，而且不是全量注入，是根据问题检索相关的表和指标再组装上下文——这样省 token，我实测过，全量注入的成本高约 44%。

第二个是 SQL 安全。因为模型可能生成危险语句，我做了多层防护：用 SQL 解析器做 AST 级校验，只允许只读查询；加上强制 LIMIT、查询超时、扫描行数上限；数据库用只读账号。这里我特意没用字符串匹配，因为注释、大小写、别名都能绕过它。

第三个是自修正循环。查询报错的时候，我不是把异常抛出去，而是把错误信息和表结构一起回灌给模型，让它在上下文里自己改，最多修正三次。

**【评测，20 秒】**

最后是我觉得最重要的部分——评测。因为数据分析的结果是可验证的，同一句问句标准 SQL 的结果集是确定的，所以我做的是结果集精确比对，而不是靠大模型打分。我自建了 60 条评测任务，其中 20 条是对抗样本，比如问不存在的指标、表名拼错、诱导写操作。44 条有标准 SQL 的任务里，结果集一致率是 75%，数值列一致率 81.8%。而且我拆到了组件层——表选择准确率、字段选择准确率、首次执行成功率、平均修正轮数，这样能定位问题是出在语义层还是模型能力。

**【结果与钩子，15 秒】**

经过三轮迭代，**答案正确率从 61.7% 提到 75.0%，多步任务从 31.8% 提到 68.2%**；单任务平均 token 从 2.1 万降到 8.3 千，降了 61%；平均耗时 5.9 秒。另外因为底层用的是 OpenTelemetry 的 GenAI 语义规范埋点，每次运行的完整轨迹都能回放，失败案例能直接定位到是哪一步出的问题。

## 三、5 分钟版（面试官说"详细讲讲"时）

在 2 分钟版基础上，按对方兴趣展开下面四个方向之一。

### 展开方向 A：为什么这个项目难

难的地方不在"让模型写 SQL"——那个跑通 Demo 很快。难的是三件事。

第一是可靠性。模型生成的 SQL 可能语法错、可能用错字段、可能查了不存在的表，这些都还好，最怕的是语法完全正确但语义错了——比如该用净额的地方用了总额，跑出来一个看起来很合理的数字。这种错误最难发现。

第二是安全性。Agent 有了执行能力之后，就必须要能拦住它做危险操作。

第三是可验证性。这也是我做评测的原因。如果我没法证明它算对了，这个项目就没有意义，因为它给出的错误结论可能比不给结论更糟。

### 展开方向 B：评测体系怎么设计的

我分了三层。

最底层是结果集比对，这是硬指标。每条评测任务都有标准 SQL 和标准结果集，比对时处理了排序差异和浮点误差，所以这个准确率是不可辩驳的。

中间是过程指标：表选择准确率、字段选择准确率、首次执行成功率、平均修正轮数。这几个指标合起来能定位问题——如果表选对了但字段老用错，说明语义层的字段描述不够；如果首次成功率低但最终准确率高，说明自修正机制在正常工作。

最上层是端到端指标，加上成本和延迟。

另外我专门造了 20 条对抗样本，包括问不存在的指标（应该拒答而不是编）、表名拼错（应该纠正）、诱导写操作（必须拦截）、还有口径歧义，比如"上月销售额"是自然月还是滚动 30 天，应该反问澄清。

### 展开方向 C：踩过的坑

有一个坑我印象比较深。我一开始给整轮对话外面包了一层重试，觉得这样更健壮。结果发现它会把整轮重放，包括那些已经成功的工具调用——如果中间有生成报告或者发通知这类操作，就会重复执行。

排查之后我把重试下沉到了单次工具调用，并且给写操作加了幂等键，整轮只保留熔断。改完之后重复副作用的问题就没有了。

还有一个是评测集本身的。我最早图省事，全部用大模型生成问答对，跑出来完成率很高，但我自己手动试了 20 次，明显感觉没那么好。后来发现生成的问题都太标准、太客气，和真实用户口语化、带错别字、跳着问的表达完全不一样。改成要求口语化生成加人工全量校验之后，基线从 89% 掉到了 61%。这个 61% 才是有意义的真实起点。

第三个坑尤其值得讲，因为它说明你会怀疑自己的数据。

### 展开方向 D：语义层为什么要做成编译器

语义层第一版是每个指标手写一段 SQL，连 join 也手写。做到十来个指标就暴露出两个问题：
比率和差值类指标（净成交额、客单价、退款率）的业务关系在多个地方重复出现，改一处漏一处；
join 关系明明是数据模型的元数据，却被抄进了每个指标里。

后来我改成行业里的做法：表关系单独声明，指标分基础指标和派生指标两类。派生指标只写
业务关系，比如净成交额就是 `{gmv} - COALESCE({refund_amount}, 0)`。剩下的交给编译器——
沿关系图找 join 路径、把归期统一到父指标指定的时间字段、跨表的各自聚合后按维度对齐再计算、
同一张表的合并成一次扫描。整个过程还能检测循环依赖，并主动报出 join 导致行数膨胀的风险。

这里有个细节可以说：退款金额默认按退款发生时间归期，但算净成交额时必须改成按所退订单的
支付时间归期。我的做法是让父指标的归期主体覆盖子指标的默认值，编译器负责贯彻到子查询里，
这条业务决定只写在一个地方。

最后我补了一步反向校验：编译出来的 SQL 跑出的结果，必须和评测集里的参考 SQL 一致。
理由是这两者是两份独立写下的口径，如果两边不一致，会出现最危险的情况——Agent 一直按
错的口径算，而评测显示通过，因为评委参考的也是错的那份。这一步跑起来当天就抓出三条任务
标注错误。面试里讲这个，比讲"我用了个什么框架"有说服力得多。

## 四、追问地图

面试官会从哪切入，你往哪答。提前知道自己每个点下面藏着什么。

| 面试官追问 | 你答什么 | 别答成什么 |
| --- | --- | --- |
| 为什么不用现成的 BI 工具？ | BI 解决固定看板的展示，解决不了自然语言的探索式分析，也不支持 Agent 自动修正 | 不要说"BI 太老了" |
| 为什么生成 SQL 不生成 pandas 代码？ | SQL 可审计、可下推执行、结果可精确比对；pandas 代码难以做安全校验 | 别说"SQL 更简单" |
| 你怎么保证它不写危险 SQL？ | 五层防护：AST 校验、语句白名单、资源限制、只读账号、审计日志 | 别说"我用了正则" |
| 结果集比对怎么处理排序和浮点？ | 排序后比对加浮点容差，说明阈值怎么定的 | 别说"直接比对字符串" |
| 语义层里放了什么？ | 表粒度、字段含义、枚举值、指标口径、注意事项 | 别说"就是字段注释" |
| 上下文怎么组装的？ | 按意图检索相关表和指标，不是全量注入 | 别说"全部塞进去" |
| 评测集怎么来的？ | 合成加人工全量校验，说明生成时要求口语化和错别字 | 别说"大模型生成的" |
| 消融实验做过吗？ | 每个模块单独开关跑对照，说明各模块贡献 | 别答"没做" |
| 你这个项目跟 Text-to-SQL 论文的区别？ | 论文是单轮映射，我做的是多步、可自修正、可审计、可评测的完整系统 | 别陷入比模型精度 |
| 有多少人用？ | 如实说：目前主要是我自己在用，或者开源后有 N 个人试过 | 不要编 |

## 五、讲的时候不要做的事

| 不要做 | 原因 |
| --- | --- |
| 一上来讲技术栈 | 面试官不关心你用了什么，关心你解决了什么 |
| 背景讲超过 30 秒 | 背景是引子，不是主体 |
| 堆技术名词 | "我用了 LangGraph、Pydantic、OTel、RAGAS、DeepEval"——听完没有任何信息量 |
| 只讲"做了"不讲"为什么" | 面试官要判断的是你的思考，不是功能列表 |
| 编用户量或上线数据 | 追问三个问题就穿帮 |
| 讲到没有数字 | 没有数字的成果等于没有成果 |
| 一口气讲完 5 分钟 | 留出被打断的空间，每个段落之间停顿一下 |

## 六、练习方法

1. **录音**：用自己的话说一遍 2 分钟版，回听。你会发现很多"然后""就是说"这类填充词。
2. **找人当面试官**：让对方随机打断你，从追问地图里挑问题。能不能接住，练三次就顺了。
3. **限制时间**：30 秒版必须真的 30 秒能说完。说得太长说明你还没抓住重点。
4. **准备一页纸**：把追问地图抄成一页，面试前看一眼。

**判断标准**：如果你讲完之后，面试官接的第一句话是"你说的那个评测体系是怎么做的"，那你讲成功了，因为你把他引导到了你最强的部分。
