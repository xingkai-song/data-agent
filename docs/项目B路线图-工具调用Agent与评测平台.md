# 项目 B 路线图：工具调用型 Agent + 评测/可观测平台

目标：产出一个能被面试官深挖 30 分钟、经得起追问的项目
周期：MVP 约 3 周，加分项再加 2 周
时效：2026 年 10 月

---

## 一、终局目标（Definition of Done）

项目做完时，你手上必须有三样东西：

1. **一个能跑的 GitHub repo**：有完整代码、README、架构图、`pytest` 测试、CI 配置
2. **一张指标表**：基线 → 优化后 → 消融实验，全是真实跑出来的数字
3. **三个能讲 20 分钟的踩坑故事**：有现象、有排查过程、有解决方案、有数据验证

第 3 条最容易被忽略，但它在面试里的权重最高。**面试官记不住你用了什么框架，但会记住你踩过什么坑、怎么爬出来的。**

## 二、面试验收标准（这是路线图的真正目标）

路线图的每一步都是为了让你能回答下面这些问题。**做不到这些，项目做得再漂亮也没用。**

| 面试官会问 | 你的项目必须具备 | 验收方式 |
| --- | --- | --- |
| 你的 Agent 任务完成率多少？怎么测的？ | 60 条评测集 + 自动化评测器 + 报告 | 能现场打开报告，说出每一条指标的算法 |
| 评测集怎么来的？ | 合成 + 人工校验，有标注一致率 | 能讲清生成流程和人工抽检比例 |
| 工具调用失败怎么处理？ | 异常分类 + 重试 + 熔断 + 幂等键 | 能演示 5 类故障的自动恢复 |
| 怎么保证不重复执行有副作用的操作？ | 幂等键设计 | 能演示重试后用户只收到一封邮件 |
| 上下文太长怎么办？ | 工具结果截断/摘要 + 缩减策略 | 有优化前后的完成率对比数据 |
| 成本和延迟怎么控制？ | token 统计 + 缓存 + 模型路由 | 有成本下降的具体数字和归因 |
| 怎么知道失败在检索层还是生成层？ | 分层指标 + 全链路 trace | 能打开 trace 指着某一步说问题在这 |
| 消融实验做过吗？ | 模块可开关 + 多组对照 | 有一张消融表 |
| 你的 Agent 会不会死循环？ | 循环检测 + 最大步数熔断 | 能讲检测机制和触发后的表现 |

## 三、技术选型（2026 年 10 月）

| 层 | 选型 | 理由 |
| --- | --- | --- |
| Agent 编排 | **LangGraph** | 2026 年生产级首选，状态机显式定义、原生 Checkpoint 持久化，天然杜绝死循环。比 `LangChain AgentExecutor` 更能体现你的设计能力 |
| 工具注册 | **Pydantic + Function Calling**；进阶用 **MCP** | MCP 已是行业共识（2026 年 9400+ 公开服务器），实现 MCP Client/Server 是强加分项 |
| 可观测性 | **OpenTelemetry GenAI 语义规范 + Langfuse** | OTel 是 2026 年统一标准；Langfuse 可 Docker 自部署、不依赖外网 |
| 评测框架 | **RAGAS（RAG）+ DeepEval（Agent/CI）** | RAGAS 拆检索/生成，DeepEval 是「AI 应用版 pytest」 |
| 测试 | **pytest** | 确定性逻辑（校验、幂等、重试）必须单测 |
| 压测 | **k6 或 Locust** | 并发、P95 |
| 成本统计 | **tiktoken** | 精确 token 计量 |
| 存储 | SQLite / PostgreSQL + Redis（缓存与幂等键） | 够用且易部署 |

**不要用**：`AgentExecutor` 三行代码跑通的那种写法。框架的封装越厚，你能讲的东西越少。

## 四、分阶段路线图

### 阶段 0｜场景与骨架（2 天）

**做什么**

选一个具体场景，不要做「通用助手」。选场景的标准是：**能自然长出多种类型的工具**。推荐：

- **数据分析 Agent**：查数据库、算统计、画图、导出报告
- **运维/研发效能 Agent**：查日志、查监控、查工单、触发部署、发通知
- **个人研究助理**：检索论文库、抓网页、总结、写入笔记

建议选第二个或第一个，工具类型最丰富。

**交付物**

- Git repo 初始化，目录结构清晰（`agent/`、`tools/`、`eval/`、`observability/`、`tests/`）
- 配置文件与密钥管理（`.env.example`，绝不提交密钥）
- 结构化日志基础

**验收**：`git clone` 后按 README 三步能跑起来一个最小 demo。

---

### 阶段 1｜工具层（4 天）——项目的核心资产

**做什么**

实现 **8–12 个工具**，必须覆盖下面四类，缺一类就会在面试里露出短板：

| 类型 | 为什么必须有 | 示例 |
| --- | --- | --- |
| 只读查询类 | 最基础，体现工具选择能力 | SQL 查询、文档检索、HTTP API 调用 |
| 计算类 | 体现沙箱隔离 | Python 代码执行（要隔离）、计算器 |
| **有副作用类** | **没有这类就讲不了幂等设计** | 写文件、发通知/邮件、提交表单 |
| **长耗时/易失败类** | **没有这类就讲不了重试熔断** | 异步任务轮询、调用不稳定的外部 API |

**关键技术点**

1. **工具注册机制**：用装饰器注册，从 Pydantic 模型自动生成 JSON Schema，避免手写 schema 出错
2. **Schema 强校验**：
   - `strict=True` 禁止隐式类型转换
   - `additionalProperties='forbid'` 拒绝模型幻觉出来的字段
   - 校验失败时把错误信息作为 Observation 回灌给模型，让它自己改（而不是直接抛错）
3. **权限模型**：给工具打权限标签（只读/写入/危险），危险操作需要确认
4. **审计日志**：谁、什么时候、调用了什么、参数是什么、结果如何

**验收**

- 每个工具有独立的 pytest 用例覆盖正常/非法参数
- 故意让模型传一个不存在的字段，验证被拦截并自动纠正
- 有副作用的工具支持幂等键

---

### 阶段 2｜执行循环（5 天）——工程质量的主战场

**做什么**

用 LangGraph 实现 ReAct 循环，并把容错做扎实。

**关键技术点**

1. **异常分类**（这是最容易被追问的地方）

   | 类型 | 举例 | 处理策略 |
   | --- | --- | --- |
   | 瞬态异常 | 网络超时、连接失败、500/502/503、429 限流 | 指数退避重试 + 抖动 |
   | 永久异常 | 参数错误、权限不足、资源不存在 | 不重试，把错误回灌给模型修正 |
   | 业务异常 | 库存不足、状态冲突 | 交给模型决策 |

2. **重试要放在正确的位置**（重要踩坑点）

   错误做法：在整轮对话外面包一层重试 → 失败后整轮重放 → 模型可能犯同样的错，还会重复执行副作用操作。

   正确做法：**在 ReAct 循环内部处理**，工具失败 → 错误作为 Observation 反馈给模型 → 模型在上下文中修正。外层只保留熔断。

3. **幂等键**：写操作带业务幂等键，相同 key 只执行一次，防止重试导致重复副作用

4. **死循环检测**（三重保险）
   - 最大步数熔断
   - 重复 `(tool_name, args)` 组合检测
   - 状态无变化检测（连续 N 步上下文没新增有效信息）

5. **上下文管理**：工具返回结果截断、超长结果摘要、只保留关键字段

6. **断点恢复**：利用 LangGraph 的 Checkpoint，任务中断后可恢复

**验收**

- 能演示 5 类故障场景下的自动恢复（超时重试成功、参数错误自动纠正、死循环被熔断、重复调用被幂等键拦住、中途崩溃后恢复）
- 有测试覆盖每种异常分类

### 阶段 3｜可观测性（3 天）

**做什么**

按 **OpenTelemetry GenAI 语义规范**埋点，导出到自部署的 Langfuse。

**Trace 结构**（按这个设计，面试时画出来很加分）

```
session（会话）
 └─ turn（一轮用户交互）
     └─ step（一个推理步骤）
         ├─ llm_call    → 模型、prompt、token、延迟
         └─ tool_call   → 工具名、参数、结果、耗时、错误
```

**关键属性**（OTel GenAI 规范里已定义的）

- `gen_ai.tool.name`、`gen_ai.tool.call.id`
- `error.type` 标准错误类型
- token 用量（input/output）、成本
- span 类型：`invoke_agent_internal`（本地推理循环）、`execute_tool`、`invoke_workflow`

**要做的能力**

1. 每次运行可完整回放：thought / action / observation 逐步可见
2. 轨迹可导出为 JSON，用于分析
3. **失败 case 自动回流到评测集**（这一步是亮点，能把可观测性和评测打通）
4. Token 与成本按 session / turn / step 聚合

**验收**：随便挑一次失败的运行，能在 Langfuse 里指出问题发生在第几步、是模型选错工具还是工具本身报错。

### 阶段 4｜评测平台（5 天）——差异化核心

**做什么**

这是整个项目最能拉开差距的部分。大部分候选人的项目根本没有评测。

**4.1 评测集（60 条）**

| 类别 | 数量 | 说明 |
| --- | --- | --- |
| 常规任务 | 20 | 覆盖各类工具的正常使用 |
| 多步任务 | 20 | 需要串联 2–4 个工具 |
| 对抗样本 | 20 | 错误参数、超时、循环陷阱、无答案、权限不足 |

构建方式：
- 从自己的文档/场景合成候选任务，**要求口语化、含错别字、含模糊指代**
- 人工校验 100%，记录标注一致性
- 每条样本包含：任务描述、期望工具链、金标准答案或验证器

**4.2 指标体系**

| 层 | 指标 |
| --- | --- |
| 工具层 | 工具选择准确率、参数填写正确率、调用成功率 |
| 任务层 | 端到端任务完成率、平均步数、无效步数占比 |
| 轨迹层 | 循环次数、错误恢复率、轨迹正确性 |
| 系统层 | P50/P95 延迟、单任务 token 成本、并发 QPS |

**4.3 评测执行器**

- 一条命令跑完全部评测集，支持并发
- 输出：JSON 原始结果 + Markdown 报告 + 指标汇总表
- 支持按类别切片分析（哪类任务最弱）

**4.4 CI 门禁**

用 DeepEval 把关键指标写成 pytest 断言，接 GitHub Actions。任何 Prompt / 模型 / 工具改动都必须通过门禁。

**4.5 LLM-as-judge（带偏差校准）**

开放式答案用 LLM 评分，但必须处理偏差：

- Rubric 结构化，输出 JSON
- 成对比较时随机交换 A/B 顺序
- 在 30–50 条人工标注样本上测评委与人类一致率，报告这个数字

**验收**：一条命令出报告；CI 能拦住指标退化；能说出每一条指标的计算方式。

### 阶段 5｜优化与消融（5 天）——产出简历数字

**做什么**

1. 跑基线，记录全部指标
2. 做 3–4 轮优化，每轮只改一个变量：
   - 工具描述更精确（Few-shot 工具说明）
   - 工具结果截断 / 摘要策略

3. **消融实验**：把每个模块单独去掉再跑一遍，用数据说明其贡献

## 六、三个必须踩的坑（讲故事的素材）

**坑 1：重试放错位置，导致重复副作用**

现象：给整轮对话加了重试，结果重试后用户收到两封邮件。
排查：发现重试触发的是整轮重放，包括已经成功的工具调用。
解决：把重试下沉到单次工具调用，给写操作加业务幂等键，整轮只保留熔断。
数据：重复副作用从每 50 次出现 3 次降到 0。

**坑 2：工具返回太长，撑爆上下文，完成率断崖下跌**

现象：接入日志查询工具后，多步任务完成率从 78% 掉到 52%。
排查：单次日志查询返回上万 token，挤掉了早期关键上下文。
解决：工具结果截断 + 关键字段提取 + 超长结果摘要。
数据：完成率回到 81%，单任务成本下降 37%。

**坑 3：评测集全用 LLM 生成，分数虚高**

现象：评测集上完成率 89%，但自己手动试了 20 次，明显感觉没那么好。
排查：LLM 生成的问题太标准、太客气，和真实口语化输入差距大。
解决：要求生成口语化、带错别字、含模糊指代的样本，并人工校验全部 60 条。
数据：修正后基线完成率从 89% 降到 61%——这才是有意义的真实基线。

第三个故事尤其加分，因为它说明你**有怀疑自己数据的意识**。

## 七、常见做偏的做法（避坑）

| 做偏了 | 后果 |
| --- | --- |
| 用 `AgentExecutor` 三行代码跑通 | 没有自己的设计，面试无话可说 |
| 工具都是 mock 的玩具函数 | 讲不了工程问题 |
| 没有有副作用的工具 | 讲不了幂等 |
| 没有易失败的工具 | 讲不了重试熔断 |
| 只评最终答案，不评轨迹 | 讲不了「蒙对」的问题 |
| 评测集全是 LLM 生成、没人工校验 | 一问就露馅 |
| 只写「用了 LangChain/LangGraph」 | 面试官会问「框架帮你做了什么，你自己做了什么」 |
| 优化做完没有归因 | 数字说不出来源，可信度打折 |

## 八、加分项（MVP 之后再做）

按性价比排序：

1. **BFCL v4 子集对标**：在公开 benchmark 上跑出分数，替代「用户量」做外部验证
2. **消融实验做细**：每个模块单独开关，出完整对照表
3. **MCP 协议实现**：把工具层做成 MCP Server，讲清 Host / Client / Server 三层与 `tools/list` 发现流程
4. **多 Agent 协作**：Planner–Executor–Critic，并对比单 Agent 的成本与收益（说明什么时候不值得用多 Agent）
5. **长期记忆**：记忆写入/检索/失效策略，并评测记忆对任务完成率的影响
6. **开源运营**：发布到 GitHub，收集 issue，把「收到 N 个 issue、修复 M 个」写进简历
