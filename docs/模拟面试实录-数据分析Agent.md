# 模拟面试实录：数据分析 Agent

面试官设定：上海头部大模型公司 Agent 岗技术面，风格接近阶跃星辰 / 字节 / 蚂蚁
候选人设定：研三，简历核心项目为「数据分析 Agent + 评测平台」，项目**尚未完成**

说明：每一轮后附【点评】，指出这题在测什么、什么样的回答会露馅。

---

## 第一轮

### Q1｜项目动机真实性　尖锐度 3

**面试官**：你说每次分析要 40 分钟，其中调试 SQL 报错花 12 分钟。这个 12 分钟是怎么统计出来的，你真的测过还是估的？另外这套分析是给谁做的，只有你自己用吗？

**候选人**：40 分钟是我自己做过几次之后记的，不是精确统计。时间分解是按环节估的，主要依据是调试 SQL 那块确实反复改，一个中等复杂度的查询平均要改两三次。目前主要是我自己在用，还没有别人用。

**点评**：这题考的是动机真实性和场景真实性。**诚实说"估的"比编一个精确数字安全得多**，因为编的数字经不起追问。但"只有我自己用"这个回答会让面试官降低项目权重，所以这里应该补一句主动的补救——比如"我计划开源出来，让同课题组的人用，收集反馈再迭代"。这不虚构，而是一个真实的计划。

**危险信号**：如果答"大概是我估计的，但应该差不多"，然后没有任何后续，面试官会认为你没认真对待这个问题。

---

### Q2｜架构合理性　尖锐度 4（最危险的一题）

**面试官**：你的架构里有语义层、9 个工具、AST 安全校验、OpenTelemetry 埋点、RAGAS 和 DeepEval 双评测框架、60 条评测集。这是一个研三学生课余时间做的项目。我想知道，这里面哪些是你已经跑通的，哪些还在设计图上？

**候选人**：目前跑通的是语义层加载、SQL 执行工具、安全校验和最小 Agent 循环；评测集有 10 条，结果集比对能跑；OTel 埋点接上了 Langfuse，能看到 trace。9 个工具里完成了 5 个，副作用类工具和幂等键还没做，评测集也还没补到 60 条。

**点评**：这是整场面试最关键的一题。**面试官在验证你是在"讲一个做过的项目"还是在"讲一个想做的项目"。**

错误答法有两种：一是硬说"都做完了"，然后后面任何一个技术细节都答不上来，整场崩塌；二是说"这只是设计，还没开始做"，那就等于承认简历上的项目是空的。

正确策略是**给出真实进度，并且进度要有结构**——说清楚哪些模块完成、完成到什么程度、下一步做什么。上面这个回答之所以好，是因为它同时证明了"你真的在写代码"和"你对自己项目的边界很清楚"。

**建议**：现在就动手做，哪怕只完成最小闭环。等到面试时，你至少要说得出"我完成了哪几块、跑了多少条评测、基线是多少"。

---

### Q3｜技术选型　尖锐度 4（陷阱题）

**面试官**：你强调用 SQL 而不是 pandas，理由是 SQL 可审计、可下推、结果可精确比对。但如果用户问的是"把这两列做个相关性分析"，SQL 写起来很别扭，你还是要退回生成 pandas 代码。那你之前说的那些优势，是不是只在查询类任务上成立？

**候选人**：确实是分层的。我的设计是查询和聚合走 SQL，复杂统计和建模走 pandas，两者分工而不是二选一。我之前说 SQL 的优势，准确讲是针对"取数和聚合"这类任务——这类任务占我分析流程的大头，而且最容易出错，所以优先用可校验的方式做。相关性分析、回归这类确实更适合 pandas，但这类计算的输入仍然是 SQL 取出来的结果集，所以校验可以分两步做：先校验取数对不对，再校验计算逻辑。

**点评**：这是陷阱题，因为它给了一个反例来测试你是不是在背理由。**承认选型有边界、并说明怎么分层，比坚持"SQL 什么都能做"得分高得多。**

这题暴露的是很多候选人的通病：把技术选型的理由背得很熟，但没想过它的适用边界。面试官一问反例就卡住。

---

### Q4｜评测方法论　尖锐度 5（陷阱题）

**面试官**：你说结果集精确比对是硬指标。那我问两个问题。第一，标准 SQL 是谁写的？如果写标准答案的人本身就理解错了口径，你是不是把一个错误固化成标准了？第二，如果底层数据每天都在变，你的标准结果集怎么维护？

**候选人**：第一个问题确实是我的方法论里最薄弱的地方。标准 SQL 是我自己写的，我参考了语义层里的口径定义和已有的分析记录。为了降低风险，我的做法是让每条评测任务在标注时同时记录"口径依据"，也就是这条标准查询为什么这么写。另外我抽了一部分拿给（导师 / 数据负责人 / 同学）复核过。但坦白说，这个环节确实是单人标注，可信度有限，如果团队里能有多人交叉标注会更可靠。

第二个问题，我的评测数据是静态快照，用 DuckDB 固定了一份数据，所以结果集是稳定的、可复现的。真实数据变化的问题我目前没有解决，如果要用在生产环境，需要一个机制在数据更新时重新生成基线，或者把断言从"结果集相等"改成"统计性质稳定"。

**点评**：这题几乎没有应届生能答好，答好了是巨大加分。

正确答法是**承认局限 + 给出缓解措施 + 说明自己知道问题在哪**。上面这个回答之所以强，是因为它同时做了三件事：承认单人标注的可信度问题、给出了"记录口径依据 + 交叉复核"的缓解方案、并且主动区分了"离线静态评测"和"生产环境动态基线"两件不同的事。

**危险答法**：坚称结果集比对是绝对可靠的硬指标。面试官会立刻追问"那标准答案错了怎么办"，你就会卡住。

---

### Q5｜工程细节　尖锐度 5（纯技术深挖）

**面试官**：你说用 AST 做只读校验。那我问个具体的。`SELECT * FROM t WHERE id IN (SELECT id FROM other)` 是只读的，没问题。但如果 `SELECT my_func(x) FROM t` 里，`my_func` 是一个有副作用的用户自定义函数呢？再比如 PostgreSQL 里 `SELECT pg_read_file('/etc/passwd')` 是完全合法的 SELECT 语法。你的 AST 校验能拦住吗？

**候选人**：拦不住。我刚才说"只允许 SELECT"其实不严谨。仅靠语句类型判断不够，因为问题出在**函数调用**上，不是语句类型上。要做的是三层：语句类型白名单、函数白名单（只允许聚合和标量函数，禁止系统函数、文件函数、以及未知的自定义函数）、还有权限兜底（数据库只读账号 + 禁止访问系统表）。你说的 `pg_read_file` 属于第三层的系统函数，应该在函数黑名单里。

另外还有一个我没想到的角度：`SELECT ... INTO` 也是 SELECT 开头但会产生写操作，这个要在 AST 层面单独拦。

**点评**：这题是纯技术深挖，装不了。**能答出"我刚才说错了，只靠语句类型不够，真正的风险点在函数调用"——这种当场修正反而非常加分**，因为它说明你在真实思考而不是背设计。

如果答"我用了 sqlglot 做 AST 校验，肯定能拦住"，面试官会继续问"那你说说 sqlglot 怎么识别函数调用的副作用"，然后就崩了。

**这题的教训**：你简历上写"AST 级 SQL 安全校验"的时候，必须真的知道它拦得住什么、拦不住什么。**任何安全相关的能力，面试官都会用具体绕过手法来测。**

## 第二轮（根据回答继续深挖）

### Q6｜代码验证　尖锐度 5

**面试官**：你刚才说完成了最小闭环和 10 条评测。能打开仓库让我看看吗？我想看看你的 Agent 循环是怎么写的。

**点评**：**这是必然会发生的。** 面试官对"自己做的项目"最直接的验证方式就是看代码。所以：

- 代码必须能公开访问（GitHub）
- README 要能让面试官 3 分钟内跑起来
- commit 记录要真实（不要最后一次性提交，那看起来像抄的）
- 不要有大量 AI 生成的痕迹而未加整理

如果代码还没准备好，就跟面试官说清楚现在到哪一步，别硬撑。

---

### Q7｜评测过拟合　尖锐度 4

**面试官**：机器学习里模型会在测试集上过拟合。你的评测集只有 60 条，而你迭代了好几轮，每次都是看着这个分数在调。你怎么保证你不是在评测集上过拟合？

**候选人**：确实有这个风险，我的做法是留出一部分不参与迭代的 holdout 集，调优只用开发集，最后才在 holdout 上跑一次。另外我关注的不只是总分，还有分项指标，如果某项指标提升但另一项下降，说明可能是过拟合而不是真的改进。

**点评**：这个追问非常有水平，也是很多人没想到的。**"评测集 holdout"这个答案能直接说明你懂评测的方法论，而不是把评测当成一个打分的脚本。**

建议真的在项目里做这件事：60 条里分出 40 条开发集、20 条 holdout，简历上可以写"在未参与调优的 holdout 集上验证"。

---

### Q8｜优先级判断　尖锐度 3

**面试官**：如果这个项目只能保留一个模块，其他都砍掉，你保留哪个？为什么？

**候选人**：保留评测。因为 Agent 本身——连数据库、生成 SQL、执行、修正——这个循环开源社区已经有很多实现，我做得比别人好的地方不在循环本身，而在于我能证明它可靠。评测没了，这个项目就退化成一个普通的 Text-to-SQL Demo。

**点评**：这题考的是你知不知道自己项目的核心价值在哪。**如果答"保留 Agent 循环"或者"都很重要"，说明你对自己项目没有判断力。**

上面这个回答之所以好，是因为它同时呼应了项目背景里的立意——"不做评测这个项目就不成立"。

## 三个真正的危险区

从这八道题里能看出，你的项目有三个地方最容易被击穿：

| 危险区 | 会被怎么打 | 怎么补 |
| --- | --- | --- |
| **项目还没做出来** | "哪些跑通了，哪些在设计图上" + "打开代码看看" | 现在就动手，至少完成最小闭环 + 10 条评测 + 真实基线 |
| **安全校验的理解停在名词层面** | 用具体的绕过手法提问（函数副作用、`SELECT INTO`、系统函数） | 真的用 sqlglot 实现一遍，并写对抗测试验证拦住/拦不住什么 |
| **金标准本身的可靠性** | "标准答案写错了怎么办""数据变了怎么办" | 记录口径依据 + 交叉复核 + 明确区分离线静态评测与生产动态基线 |

---

## 这场模拟面试反过来给你的行动清单

面试官问的问题，其实就是你接下来该先做的东西：

1. **把最小闭环跑通并推到 GitHub**——这是 Q2 和 Q6 的答案基础，也是所有数字的来源
2. **真做一遍 SQL 安全校验并写对抗测试**——Q5 暴露的问题只有动手才能补，而且对抗测试本身就是简历素材
3. **评测集分出 holdout 集**——Q7 的答案，成本很低但显得专业
4. **给你的评测加"口径依据"字段**——Q4 的答案，同时能体现你对数据治理的理解
5. **测一次真实耗时**——下次做分析时记个时间，Q1 就有真实数字了

做完这五件事，上面八道题里有六道你能答得很稳。
