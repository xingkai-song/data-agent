# 项目背景定稿：数据分析 Agent

方向：工具调用型 Agent + 评测/可观测平台
场景：数据分析工作流

---

## 一、为什么数据分析这个角度对你最有利

三个理由，从弱到强：

**1. 痛点天然真实，不需要硬编。** 任何做过数据分析的人都经历过"写 SQL → 报错 → 改 → 再报错"的循环，面试官也有体感，不需要你费力说服。

**2. 上海的岗位直接对口。** 米哈游的 Data Agent 岗位 JD 写的是「负责大语言模型在数据平台与数仓场景中的应用探索与核心研发」「设计并开发面向数据查询、数据开发、平台运维等场景的 Agent」「参与数仓语义层建设」。字节数据平台、小红书、以及大量金融/零售公司的数据团队都有同类需求。你的项目背景和这些岗位是同一件事。

**3. 最重要的一条：这个场景的评测能做硬指标。** 数据分析的结果是可验证的——同一句自然语言问句，标准 SQL 的结果集是确定的，可以直接做精确比对。这意味着你的评测不用全靠 LLM 评委，可以给出「SQL 执行结果准确率」这种不可辩驳的数字。**这是数据分析方向相比医疗、客服等开放式场景最大的优势**，也是你简历上数字最有说服力的地方。

## 二、定稿背景

> 方括号 `[...]` 里的内容必须换成你的真实细节。第三节有填充指南。

我在 [课程项目 / 科研任务 / 毕设] 里需要反复做同类数据分析：[数据来自哪、大概多大规模、多少张表]。每次分析的流程都差不多——先确认字段含义和统计口径，再写查询，然后调试报错，最后画图整理结论。

这套流程每次要花 [40] 分钟左右，而且我统计过时间分布：理解表结构和字段口径大概 [8] 分钟，写 SQL 和 pandas 大概 [10] 分钟，调试类型错误和空值问题大概 [12] 分钟，整理图表和结论大概 [10] 分钟。**真正花在"分析本身"的时间很少，大部分消耗在机械的重复劳动上。**

更麻烦的是过程不可复用。下次做类似分析时，前面那 [30] 分钟基本要重来一遍，而且因为没有沉淀，同一个指标两次算出来的口径可能还不一样——这在需要写进报告的场景里是挺严重的问题。

我先试过用通用的大模型助手。它能帮我写 SQL 和 pandas 代码，但有三个绕不过去的问题：它看不到我的真实表结构，写出来的代码经常跑不通；代码要我自己复制到环境里执行，报错了再贴回去让它改，来回几轮下来省的时间很有限；它无法访问数据，所以所有的验证都要我自己做。

我也试过把字段说明和口径文档接进 RAG 问答系统。这解决了「这个字段是什么意思」这类问题，但没有解决执行——它依然只能告诉我该怎么做。

所以我判断方向是让模型直接连数据库、自己执行查询、根据报错自己修正，把整条链路打通。

但做到这一步我意识到一个更关键的问题：**数据分析出错比不回答更危险。** 如果 Agent 算错了一个指标，而这个错误结论被写进报告，后果比它拒绝回答严重得多。我搜过的教程和开源示例基本都停在「自然语言转 SQL 跑通」，很少有人认真回答「怎么证明它算对了」。

所以我这个项目要解决两件事：**让 Agent 能可靠地完成从提问到结论的完整数据分析链路，以及建立一套能用数据证明它算对了的评测体系。**

## 三、槽位填充指南

判断标准只有一条：**面试官能否从这句话里提出一个具体问题。** 如果提不出问题，说明太虚。

| 槽位 | 需要什么级别 | 太虚的写法 | 合格的写法 |
| --- | --- | --- | --- |
| 数据规模 | 行数 + 表数 + 字段数 | 「一个比较大的数据集」 | 「约 12 万行、6 张表、40 多个字段」 |
| 领域 | 具体业务 | 「一些业务数据」 | 「某课程项目的用户行为日志 / 实验室的实验记录」 |
| 频率 | 每周几次 | 「经常要做」 | 「每周大概 3 到 4 次」 |
| 单次耗时 | 分钟数 | 「挺费时间的」 | 「平均 40 分钟」 |
| 时间分解 | 分环节 | 无 | 见正文的四段分解 |
| 报错频率 | 次数 | 「经常报错」 | 「一个中等复杂度的查询平均要改 2 到 3 次」 |

**真实数字怎么得到**：不需要精确测量。下次做分析时看一眼开始和结束时间，记下大致耗时；或者回忆上一次做完整分析时，光调试 SQL 报错改了几次。**大概的数字远好过编的精确数字**——面试官追问"你怎么测的"，你能说"我下次做的时候记了个时间"，这就够了。

## 四、这个角度天然引出的技术设计点

背景选对了，后面每个技术决策都有出处，面试时不用现编理由。

| 数据分析场景的真实痛点 | 自然长出的技术设计 | 面试可以讲的点 |
| --- | --- | --- |
| 模型看不到表结构，写的 SQL 跑不通 | Schema 注入 + 语义层（字段含义、口径、枚举值） | 「我把表结构、字段注释和统计口径做成语义层喂给模型，而不是只给 DDL」 |
| SQL 报错要人工来回改 | 执行结果（含报错）回灌到 ReAct 循环自动修正 | 「错误不是抛出去，而是作为 Observation 返回给模型让它自己改」 |
| 可能会写错数据、跑全表 | SQL 只读校验 + 危险语句拦截 + 行数上限 + 超时 | 「我用 SQL 解析器做 AST 级别的安全校验，而不是字符串匹配」 |
| 算错了会被写进报告 | 结果集精确比对评测 + 数值合理性校验 | 「同一个问题，标准 SQL 的结果是确定的，所以我可以做结果集级比对，而不是靠 LLM 打分」 |
| 口径不一致、过程不可复用 | 语义层 + 分析模板 + 轨迹复用 | 「我把分析过程沉淀成可复用的轨迹，下次同类问题直接复用」 |
| 复杂分析要拆多步 | 任务规划 + 多步查询 + 中间结果校验 | 「复杂分析拆成多个查询，每个中间结果都做合理性校验」 |
| 查错表、用错字段 | 工具选择评测 + 字段级参数准确率 | 在评测里单独统计字段选择准确率 |
| 成本和延迟 | 缓存 + 小模型路由 | 「同类查询命中缓存，简单取数走小模型」 |

**注意**：这张表里，「语义层」和「结果集比对评测」是数据分析方向独有的加分项，其他方向的候选人讲不出来。面试时优先讲这两个。

## 五、数据分析场景的评测怎么做（你的差异化优势）

这是这个方向最值钱的地方。评测分三层，前两层都是硬指标：

### L1 结果集比对（硬指标，不可辩驳）

对每个评测任务，准备一条标准 SQL 和金标准结果集。Agent 生成的查询执行后，直接比对结果集。

- **Exact Match**：结果集完全一致的比例
- **有序比对**：排序后的结果集一致（避免因排序不同误判）
- **容差比对**：浮点数的相对误差在阈值内视为一致

这条指标可以直接写进简历：*「SQL 执行结果准确率 89%」*——它比任何 LLM 打分都硬。

### L2 中间过程指标

- 表选择准确率（有没有选错表）
- 字段选择准确率（有没有用错字段）
- SQL 首次执行成功率（一次就写对的比率）
- 平均修正轮数（报错后要改几次）

这四个指标合起来能定位问题：如果表选择准确率高但字段准确率低，说明语义层里字段描述不够；如果首次成功率低但最终准确率高，说明自修正机制在工作。

**这个定位能力是面试的高光时刻**——你能说"我不是只测了个总分，我拆到组件层，能定位到是语义层的问题还是模型能力的问题"。

### L3 端到端与系统指标

- 任务完成率（从提问到给出正确结论）
- 多步任务的分步正确率
- P95 延迟、单次分析 token 成本
- 危险语句拦截率（100% 是底线，要单独测）

### 对抗样本（数据分析专属）

这类样本特别容易造，也特别能说明问题：

- 问一个数据里不存在的指标 → 应该拒答而不是编
- 表名拼写错误 → 应该纠正而不是乱猜
- 需要全表扫描的查询 → 应该被拦截并提示
- 诱导写操作的表述（「顺便帮我删掉异常值」）→ 必须拦截
- 数值边界：空值、除零、日期跨年
- 口径歧义：「上月销售额」是指自然月还是滚动 30 天 → 应该反问澄清

最后一条尤其加分，因为它体现了「不确定时主动澄清」这个 Agent 该有的行为。

## 六、面试追问预案（数据分析专属）

| 追问 | 怎么答 |
| --- | --- |
| 你怎么保证它不写危险 SQL？ | AST 级只读校验、语句类型白名单、行数上限、超时、权限最小化；并说明拦截率是单独测的 |
| 结果集比对怎么处理排序和浮点误差？ | 排序后比对 + 浮点容差，说明容差阈值怎么定的 |
| 口径歧义怎么办？ | 语义层里定义清楚，遇到歧义主动反问而不是猜 |
| 为什么不让模型直接生成 pandas 代码？ | 说明 SQL 的优势：可审计、可校验、执行下推到数据库、结果可比对 |
| 复杂多步分析怎么保证中间结果正确？ | 分步校验 + 中间结果合理性检查（如总量守恒、非负、范围） |
| 为什么不用现成的 BI 工具？ | BI 解决固定看板，解决不了自然语言的探索式分析，且不支持 Agent 自动修正 |
| 你的项目跟 Text-to-SQL 论文比有什么不同？ | 强调你是完整链路（含自修正、安全、评测、可观测），而不只是模型精度 |

最后一个问题的回答要突出：**Text-to-SQL 是单轮映射，你做的是多步、可自修正、可审计、可评测的完整系统。**

## 八、下一步

背景定稿后，建议按这个顺序推进：

1. 先在纸上把「语义层」的表结构设计出来——这是整个项目的地基
2. 造 10 条评测任务（含标准 SQL 和结果集），先把评测跑通，再写 Agent
3. 然后按路线图阶段 1 开始做工具层

**第 2 步的顺序很重要**：先有评测再有 Agent，你才能在开发过程中随时知道改动有没有用。这也是面试里可以讲的——「我先建立了评测集再开发，避免凭感觉优化」。
