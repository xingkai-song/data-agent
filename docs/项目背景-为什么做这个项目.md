# 项目背景：为什么要做这个项目

用途：简历项目描述的开头、README 的动机段落、面试「为什么做这个项目」的口述

---

## 一、先说清楚：背景的作用是什么

面试官问「为什么做这个项目」，实际在验证三件事：

1. **你是因为追风口，还是真有判断？** 前者一问就穿。
2. **你对问题的理解有多深？** 背景讲得越具体，说明你越接近真实问题。
3. **后面的技术选型是不是被问题逼出来的？** 好的背景会让技术决策显得"不得不这么做"。

所以背景不能是"我想学 Agent 技术"，必须是**「我看到一个具体的、真实的痛点 → 现有方案解决不了 → 所以我要做这个」**。

关键：**可信度来自具体，不来自宏大。**「解决 AI 落地最后一公里」这种话对一个学生项目来说是减分项；「一次数据分析要在三个工具之间来回跳，平均 40 分钟」才是加分项。

---

## 二、背景的四段式结构

| 段落 | 要说什么 | 禁忌 |
| --- | --- | --- |
| 1. 场景 | 我在什么场景下、反复遇到什么麻烦 | 不要宏大叙事 |
| 2. 痛点的代价 | 这件事有多费时间 / 多容易出错 | 不要只有形容词，要给量级 |
| 3. 现有方案为什么不行 | 通用助手 / 纯 RAG 分别卡在哪 | 要具体到"它只能给方案不能执行" |
| 4. 我要解决什么 | 核心矛盾是什么 | 要引出技术主线，不要只是"做个 Agent" |

第 4 段最重要：**它必须自然引出「工具调用 + 评测」这两条主线**，这样后面你做的所有技术设计都有出处。

---

## 三、推荐叙事（主版本）

> 下方括号里的内容，请替换成你真实的细节。**如果你其实没接触过这个场景，就换一个你真实的，不要硬套**——面试官一定会追问细节。

### 背景正文

在研究生阶段的科研和课程工作里，我每天都在处理分散的信息和重复的数据操作：查文献、翻历史实验记录、跑统计脚本、整理成报告。这些事单看都不难，但切换成本极高——一次完整的数据分析要在文档、数据库、Python 环境之间来回跳，平均要花（40）分钟以上，而且每次都要重新回忆上次的查询口径和步骤。

我先试过用通用的大模型助手来解决，但很快发现一个根本局限：**它只能告诉我怎么做，不能替我做。** 问它「我（上周那组实验/上个季度的销售）的指标是多少」，它教我写一段 SQL；问它「帮我看看这段日志里的异常」，它给我一段分析思路。真正的执行还是得我自己来。

我也试过把资料接进 RAG 问答系统。这解决了「查得到」的问题，但没有解决「做得了」的问题——它依然只能给答案，不能执行操作。

所以我判断真正有价值的方向，是让模型能**调用工具去执行**：查数据库、跑脚本、读文件、生成报告。

但这就引出了一个更关键的问题：**当模型开始真正执行操作时，我怎么知道它做对了？**

如果没有可靠的评测手段，一个会执行操作的 Agent 比一个只会聊天的助手更危险——它可能查错数据、算错指标，甚至执行错误的写操作。而当时我看到的大部分教程和开源示例，都停在「跑通一个 Demo」，没有人认真回答「怎么证明它可靠」。

所以这个项目从一开始要解决两件事：**让 Agent 可靠地调用工具执行任务，以及建立一套能证明它可靠的评测体系。**

### 为什么这个叙事站得住

- **起点是真实体验**，不是"我想学新技术"
- **有具体的量化痛点**（40 分钟、三个工具之间切换）
- **对现有方案的批评是技术性的**（"只能给方案不能执行"），不是情绪化的
- **最关键**：它让「评测」变成项目成立的前提，而不是后期硬加的模块。面试官问"你为什么要花时间做评测"，你的回答是"因为不做评测，这个项目根本不成立"——这个逻辑链条非常有力

## 四、三个场景变体（挑一个贴合你真实情况的）

### 变体 A：课题组知识传承

适用：在实验室待过、带过师弟师妹、或自己接手过师兄的代码和数据

> 我们课题组（有 N 个人）积累了大量论文、实验记录和代码，但知识高度分散。新同学上手时大量问题要靠问师兄师姐，同一个问题（某个指标怎么算、某份数据在哪、某段脚本怎么跑）每年都要被问很多遍，师兄师姐每周要花（几小时）重复回答。
>
> 我尝试做过一个文档问答系统，但它只能回答「是什么」，回答不了「帮我把这个跑一遍」「帮我查一下这个数据」——而后者才是真正费时间的部分。
>
> 所以我需要的是一个能真正执行操作的 Agent：查文档、查实验数据库、跑分析脚本、生成结果报告。

**优势**：知识传承的痛点非常真实，且"只能回答不能执行"的批评天然成立。

### 变体 B：数据分析工作流

适用：做过数据分析类项目、课程作业或实习

> 我做的（课程项目/科研任务）需要反复做同类数据分析：连数据库、写 SQL、用 pandas 清洗、画图、整理成结论。每次结构都差不多，但每次都要重写一遍，一次要花（半小时到一小时）。
>
> 大模型能帮我写 SQL 和 pandas 代码，但代码要我自己贴到环境里跑、报错了再贴回去改，来回几轮下来时间并没有省多少，而且它看不到我的真实数据结构，经常写出跑不通的代码。
>
> 我需要的是能直接连数据库、自己执行、自己根据报错修正的 Agent。

**优势**：痛点具体、可量化，且能自然引出"工具结果回灌修正"这个技术点。

### 变体 C：服务运维与值班

适用：参与过实验室服务器维护、学生团队运维、或做过后端项目

> （实验室/团队）的服务器和服务由学生轮流维护，出问题时排查流程很分散：要先看监控、再翻日志、再查有没有相关工单，故障处理经验大多留在个人脑子里。
>
> 我试着整理成文档，但真正出故障时没人会去翻文档，还是习惯直接问人。文档问答也解决不了问题——它能告诉我"日志在哪"，不能替我去查。
>
> 所以我需要的是一个能真正查日志、查监控、查工单、并给出判断依据的 Agent，而且因为涉及重启服务这类危险操作，它必须足够可靠、可审计。

**优势**："涉及危险操作"这一点能极自然地引出幂等、权限、审计日志的设计，也让「必须做评测」变得不可回避。

## 五、背景 → 技术决策的对应关系

面试官追问"你为什么要这么做"时，用这张表回答。**每个技术决策都要能在背景里找到出处**，这样你的设计才显得是被问题逼出来的，而不是照抄教程。

| 你的技术决策 | 背景里的哪句话支撑它 |
| --- | --- |
| 为什么要工具调用，不做纯 RAG | 「它只能给答案，不能执行操作」 |
| 为什么要 8 个以上工具、还要分四类 | 真实任务本来就跨多种操作，工具太单一撑不起真实场景 |
| 为什么写操作要幂等键 | 场景里有「生成报告/发通知/写文件」，重试必须安全 |
| 为什么重试要下沉到单次调用 | 整轮重放会重复执行已成功的副作用操作 |
| 为什么要有轨迹日志 | 只看最终结果无法判断 Agent 是推理出来的还是蒙对的 |
| 为什么要做评测体系 | 「不做评测，这个项目根本不成立」——这是背景的核心 |
| 为什么要对抗样本 | 真实使用中我就遇到过参数幻觉、循环、超时这些问题 |
| 为什么要评成本和延迟 | 我的原始痛点是"省时间"，如果 Agent 又贵又慢就没有意义 |
| 为什么要有权限模型 | 场景里有危险操作，不能让它随便执行 |
| 为什么用 LangGraph 而非现成 AgentExecutor | 需要显式控制状态转移和熔断条件，不能黑盒 |

## 六、面试口述版（约 90 秒）

> 这个项目的出发点是我自己科研里的一个真实麻烦。我每天要在文档、数据库和 Python 环境之间来回切换，做一次完整的数据分析平均要 40 分钟以上，而且每次都要重新回忆上次的查询口径。
>
> 我先用了通用大模型助手，但发现它只能告诉我怎么做，不能替我做——问它某个指标是多少，它教我写 SQL；问它日志有什么异常，它给我分析思路，执行还是我自己来。后来我又试了 RAG 问答，解决了"查得到"，但没解决"做得了"。

> 所以我判断方向是让模型能调用工具去真正执行。但做到这一步我意识到一个更关键的问题：当它开始真的执行操作时，我怎么知道它做对了？如果它查错了数据、写错了文件，比一个只会聊天的助手更危险。
>
> 而我看的大部分教程和开源项目都停在「跑通 Demo」，没人认真回答「怎么证明它可靠」。所以我这个项目要解决的就是两件事：让它可靠地调用工具执行，以及建一套能证明它可靠的评测体系。

## 七、背景里绝对不能出现的话

| 不能说的话 | 为什么 |
| --- | --- |
| 「我想学习 Agent 技术/框架」 | 直接把项目定性成练手，后面所有内容的权重都下降 |
| 「因为 Agent 现在很火、岗位多」 | 暴露动机是求职而非解决问题 |
| 「我要打造一个通用 Agent 平台」 | 学生项目做不出来，一问范围就崩 |
| 「为解决 AI 落地最后一公里」 | 宏大且空洞，显得没有真实体感 |
| 编造的用户量、团队规模、上线数据 | 一旦被追问细节就穿帮，风险极高 |

**一条底线**：背景里的场景必须是你真实接触过的。可以重新组织语言、可以突出痛点，但不能虚构一个你没经历过的场景——面试官会追问"你们实验室几个人""这份数据多大""你当时具体怎么做的"，编的场景撑不过三个问题。

## 八、追问预案

面试官针对背景最可能追问的问题，提前准备好真实答案：

| 追问 | 你要准备的 |
| --- | --- |
| 你这个痛点有多严重？有数据吗？ | 具体耗时、发生频率、涉及多少人 |
| 你为什么不用现成的产品？（如各类 AI 助手、Copilot） | 说清它们的边界：不接你的数据、不能执行、不能审计 |
| 为什么不用 RAG 就够了？ | 回答"查得到"和"做得了"是两件事，并举例 |
| 这个项目有多少人用？ | 如实说：目前主要是我自己在用 / 开源后有 N 个人试过。**不要编** |
| 你觉得最大的难点是什么？ | 说"可靠性验证"——这和你的评测体系呼应 |
| 如果重做一次你会改什么？ | 例如"会更早建立评测集，因为前期的优化都是凭感觉，有了基线才知道每次改动有没有用" |

最后那个问题的答案尤其加分，因为它体现你会反思方法论。
