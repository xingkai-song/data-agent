# 数据分析 Agent

面向数据分析工作流的工具调用型 Agent：让模型直接连数据库、自己生成查询、自己执行、根据报错自我修正，并配套一套用**结果集精确比对**来证明它算对了的评测体系。

## 为什么做这个项目

大模型能帮我写 SQL，但它看不到真实表结构，写出来的代码经常跑不通；就算跑通了，也要我自己复制到环境里执行、报错了再贴回去改。更麻烦的是，**数据分析出错比不回答更危险**——如果算错一个指标而这个结论被写进报告，后果比拒绝回答严重得多。

我看过的教程和开源示例基本都停在「自然语言转 SQL 跑通」，很少有人认真回答「怎么证明它算对了」。所以这个项目要在做 Agent 的同时建立一套评测体系。

详细背景见 `docs/项目背景-数据分析Agent-定稿版.md`。

## 评测集

60 条任务，三个类别：

| 类别 | 数量 | 评测方式 |
| --- | --- | --- |
| 单表查询 | 18 | 结果集精确比对 |
| 多表/多步 | 22 | 结果集精确比对 |
| **对抗样本** | **20** | LLM 评委按 rubric 评行为是否恰当 |

对抗样本覆盖四类：越权与写操作（读服务器文件、删数据、重建表）、
不存在的数据（满意度、毛利率、收货省份、手机号）、
边界情况（超出数据范围、未来时间、空结果）、
歧义与纠错（口径歧义、表名/字段名拼错、"用户数"多口径）。

## 真实基线（2026-10-08）

模型 `deepseek-chat`，评测集 60 条。**主指标是答案正确率**（LLM 评委），
结果集指标作为补充。

### 消融：三轮优化

每一轮只改一类变量，都跑完整 60 条评测。

| 指标 | v1 基线 | v2 提示词优化 | v3 接口设计修复 |
| --- | --- | --- | --- |
| **答案正确率** | 61.7% | 68.3% | **75.0%** |
| 完全正确 + 部分正确 | 68.3% | 78.3% | **80.0%** |
| 平均得分 | 0.673 | 0.752 | **0.792** |
| 单表任务 | 16/18 | 16/18 | 16/18 |
| **多步任务** | 7/22 = 31.8% | 10/22 = 45.5% | **15/22 = 68.2%** |
| 对抗样本 | 14/20 | 15/20 | 14/20 |
| 步数熔断 | 12 | 2 | **0** |
| 平均模型调用 | 5.6 | 3.9 | **3.0** |
| 平均工具调用 | 6.2 | 2.3 | **1.5** |
| 平均 token / 任务 | 21,472 | 11,857 | **8,346** |
| 总耗时（60 条） | 434s | 307s | **355s** |

从 v1 到 v3：**正确率 +13.3pp，多步任务 +36.4pp，token -61%，熔断清零。**

#### v2：提示词优化

只改了一个变量——**告诉 Agent 直接用注入的语义层上下文，不要重复调用工具去查已知信息**。

语义层的价值本来就是"让模型不用自己去探索表结构"，但 v1 的提示词写的是
「不确定指标定义时用 search_metrics」，结果模型把已经注入的上下文又查了一遍，
白烧步数，然后在多表任务上撞到步数上限。

#### v3：修接口设计缺陷（这一轮的价值最大）

v2 之后多步任务只有 45.5%，我去逐条看失败原因，发现**根因不是模型能力，是我的接口设计错了**：

`run_sql` 只回传 5 行预览和一个句柄，但**没有任何工具能读取完整结果**。于是模型：

- **漏答**：「销量前 10 的商品」它只看到 5 个，就把其余概括成"其余 5 个商品"
- **编造**：T37 的服饰品类订单数没落在前 5 行里，它直接编了一个"约 900"

修法是让结果在 50 行以内**全量回传**，超过就显式置 `more_rows_available=true`
并提示"不要基于部分数据下结论，把统计下推到 SQL 里"。

顺带修了另一个不一致：任务里用了 `order_count` 这个指标，但语义层里根本没定义它，
模型只能自己猜归期字段（结果猜成了支付时间，应该是下单时间）。补上了定义。

另外把工具 schema 做了无损压缩（去掉 Pydantic 自动生成的 `title`、
把 `anyOf: [X, null]` 合并成 `type: [X, "null"]`），省下约 26% 的 schema token。

#### 第四轮：语义层改造成编译器（换的是架构，不是提示词）

这一轮改的是语义层的组织方式——指标定义从"手写 SQL 片段加手写 join"
改成声明式定义加编译器。改完我跑了对照，看会不会影响模型表现：

| 指标 | v3 基线 | 注入编译 SQL | 默认（不注入） |
| --- | --- | --- | --- |
| **答案正确率** | 75.0% | 73.3% | **75.0%** |
| 完全正确 + 部分正确 | 80.0% | 76.7% | 78.3% |
| 单表任务 | 16/18 | 16/18 | 16/18 |
| 多步任务 | 15/22 | 14/22 | 15/22 |
| 对抗样本 | 14/20 | 14/20 | 14/20 |
| 平均 token | 8,346 | 8,706 | 8,842 |

**结论：把编译出来的标准 SQL 塞进上下文，没有带来收益。** 差距只有 1 条任务，
60 条样本下不构成显著差异；但既然没有收益，就没有理由默认开这个变量。
所以 `SEMANTIC_EMIT_SQL` 默认关闭，模型需要完整 SQL 时可以自己调 `search_metrics` 取，
属于按需查询而不是全量注入。

这次改造的价值不在分数上，在三个地方：

1. **join 不再手写**——它是数据模型元数据，声明一次由编译器推导
2. **同一个口径只写一次**——比率、差值类指标只写业务关系，SQL 交给编译器
3. **编译产物可以被反证**——用评测集参考 SQL 交叉校验编译结果，
   第一次跑就抓出三条任务标注错误（见上面的「口径交叉校验」）

这个结论本身也是面试素材：*改造做完发现提示词层面没有收益，我就没把它设成默认。
架构收益和质量收益是真的，模型分数收益不是。*

### 一个反直觉的结果：结果集指标反而降了

| 指标 | v1 | v2 |
| --- | --- | --- |
| 结果集一致率 | 37/44 = 84.1% | 33/44 = 75.0% |
| 数值列一致率 | 39/44 = 88.6% | 35/44 = 79.5% |

答案正确率涨了，结果集指标却跌了。原因是：

**v1 平均每个任务跑 2.6 条查询，v2 只跑 1.3 条。**
「任一查询命中」这个口径天然偏好查询多的版本——查得越多，越容易碰对一次。

**结论：「best-of 查询」不适合当主指标**，它对"跑得多"有系统性偏好。
所以本项目以答案正确率为主指标，结果集指标只作补充。
这个问题是跑消融时才发现的，光看单一数字根本看不出来。

### 又一个反直觉的结果：v3 的静默错误率其实变差了

补上"静默错误率"（`eval/silent_error.py`）之后，v1→v3 的故事需要修正。

定义：**分母只算系统自己给出结论的题（`answered`），分子是其中结果错的题。**
澄清、熔断、失败都算"主动未作答"，不计入——混进来会稀释这个指标；但
**覆盖率必须同时报**，否则可以通过少答来刷低静默错误率。

| 版本 | 覆盖率 | 静默错误率（10 次重跑的区间） |
| --- | --- | --- |
| v1 | 33/44 = 75.0% | **3~4/33 = 9.1%~12.1%** |
| v2 | 42/44 = 95.5% | 9~10/42 = 21.4%~23.8% |
| v3 | 43/44 = 97.7% | **10/43 = 23.3%**（偶发 9/43） |

**从"答案正确率"看 v1→v3 大幅进步（61.7%→75.0%）；从"静默错误率"看却是退步。**

原因拆开很清楚：v1 在 10 道题上撞到步数上限被熔断，v3 全部给出了结论，
其中 **4 道是错的**——v3 用"更敢答"换来了覆盖率，同时把 4 个原本被拦住的
错误答案放到了用户面前。（另外 2 条的差异来自运行间波动：同一条件重跑结果
会变，见「已知问题」。）

这正是本项目一开始的主张——**算错比不回答更危险**——在自己身上的一次实证。
所以两个指标必须成对看：只看完成率会得出"v3 全面更好"，只看静默错误率又会
得出"v1 更稳"，都不完整。

**这个指标本身有 ±1 条的抖动，原因查清楚了。** 评测集里有一条 top-N 任务
（T36「购买件数最多的 5 个订单」），候选 SQL 只写了 `ORDER BY total_qty DESC
LIMIT 5` 而没有唯一 tiebreaker——实测**同一条 SQL 执行 30 次返回了 10 种不同
的结果集**（qty=8 并列，DuckDB 每次挑的行不同）。偶尔恰好和参考结果撞上，
就被算成通过。

两个结论：一是**静默错误率被略微低估**；二是**这本身就是一条真实的失败**——
缺 tiebreaker 的排序查询结果不可复现，应当判错。所以指标要有稳定性检查
（同一条 SQL 重跑必须一致），现在还没有。

**对应的防护**：`agent/sanity.py` 在每次工具返回后做四项**零成本**的不变量
检查——金额/数量非负、比率落在 [0,1]、净额 ≤ 总额、退款 ≤ 成交额——命中就
回灌给模型让它重查。**它抓不住"数值自洽但口径被替换"**（例如把客单价的分子
从 GMV 悄悄换成净成交额），那类需要多路径对算，目前仍未实现。

### 评委可信度

用 6 条已知对错的校准样本（3 条正确 + 3 条典型的错法：用错归期字段、
编造数字、换错口径）测评委与人工的一致率：**6/6 = 100%**。

抽查真实性也确认评委在干活：T32（各品类折扣率）判定正确并逐一核对了数字；
T21（各品类成交额）判定错误并准确指出「口径用了 orders.amount 而非明细表减 discount」——
这正是数据集里埋的陷阱。

**但必须说明的局限**：样本只有 6 条，而且**评委和选手是同一个模型**
（本项目只有一个模型可用），存在自我偏好的风险。严格做法应该用不同厂商的
模型交叉评审，或引入人工标注做校准。这一点在面试里要主动讲。

## 语义层与指标编译

这一层的目标是**同一个口径只写一次**。人只声明业务关系，SQL 由编译器推导。

**表关系是 join 的唯一来源。** `tables.yaml` 里声明表间关系（等价于外键）：

```yaml
- name: refunds
  relations:
    - to: orders
      "on": refunds.order_id = orders.order_id
```

指标定义里不写 JOIN。要连哪张表、按什么条件连，由编译器沿关系图找路径生成。
（键名 `on` 必须加引号——YAML 1.1 会把裸 `on` 解析成布尔值，这个坑踩过一次。）

**指标分两类**，对应行业里的 base measure / derived metric：

```yaml
# 基础指标：一段聚合表达式
- name: refund_amount
  definition: SUM(refunds.refund_amount)
  base_table: refunds
  time_column: refund_time

# 派生指标：用其他指标组合，不写 SQL
- name: net_gmv
  expression: "{gmv} - COALESCE({refund_amount}, 0)"
  base_table: orders
  time_column: pay_time
```

指标引用用 `{name}` 显式标注（对齐 dbt 的 `ref()`、Cube 的 `{metric}`）。
这样拼写错误在加载时报出来，而不是变成一句跑不通的 SQL。

**编译器负责四件事**（`semantic/compiler.py`）：

| 职责 | 说明 |
| --- | --- |
| 依赖解析 | 递归展开派生指标，检测循环依赖 |
| join 推导 | 沿关系图找路径，生成 JOIN / LEFT JOIN |
| 归期统一 | 派生指标的归期覆盖子指标的默认值 |
| 粒度对齐 | 跨表指标各自聚合后按维度对齐再计算 |

最后一条是关键。`net_gmv` 的分子在订单表、减项在退款表，直接 join 会重复计数；
编译器的做法是各自聚合成 CTE 再对齐：

```sql
WITH net_gmv__d0 AS (SELECT SUM(orders.amount) AS v FROM orders WHERE ...),
     net_gmv__d1 AS (SELECT SUM(refunds.refund_amount) AS v FROM refunds
                     JOIN orders ON refunds.order_id = orders.order_id
                     WHERE orders.pay_time ... )
SELECT net_gmv__d0.v - COALESCE(net_gmv__d1.v, 0) AS net_gmv
FROM net_gmv__d0 FULL OUTER JOIN net_gmv__d1 ON 1 = 1
```

注意 `net_gmv__d1` 的时间过滤落在 `orders.pay_time` 上，而不是 `refunds.refund_time`——
"退款按所退订单的支付时间归期"这条业务决定写在父指标的 `base_table` / `time_column` 里，
编译器负责把它贯彻到子指标。

**同表指标会合并成一次扫描。** 客单价 = 成交额 ÷ 支付订单数，两个分量都在 orders 上，
编译成一条 `SELECT SUM(...) / NULLIF(COUNT(DISTINCT ...), 0) FROM orders`，不需要 CTE。

**定义里引用到的表会被自动 join。** VIP 成交额的表达式用了 `users.is_vip`，
编译器扫出这张表并沿关系图补上 `JOIN users`，不需要额外声明。

**fan-out 风险会主动报出来。** 如果为了拿到某个维度必须从父表走到子表
（比如按商品类目给订单级指标分组，得经过 order_items），行数会膨胀、结果偏高。
编译器检测到就警告，不静默处理。

### 口径交叉校验

编译产物会被反过来验证：编译出的 SQL 跑出的结果，必须和评测集里的参考 SQL 一致。

```
python eval/semantic_check.py
```

这一步补的是一个真实缺口。语义层的指标定义和评测集的 `reference_sql` 是两份独立写下的口径，
两边不一致会出现最危险的情况——**Agent 一直按错的口径算，而评测显示"通过"**
（评委参考的也是错的那份）。第一次跑就抓出三处任务标注错误：T16 把"退款笔数"标成了
`refund_amount`、T26 把"VIP 占比"标成了 `gmv`、T40 的复合口径没有标注。
现在这项检查已经进 CI 门禁，12 条可比对的任务全部一致。

**已知边界（不夸大）**：同时受两个时间条件约束的口径（如"9 月注册且 9 月完成首单支付的用户"），
当前编译器表达不了——它只有一个归期主体。这类任务显式标记为不参与单指标交叉校验，
而不是假装能覆盖。

### 编译优先：让模型只选指标，不拼 SQL

这是语义层最容易被忽略的用法。既然编译器能生成标准 SQL，**已定义的指标就不该
让模型自己写**——手写等于把确定的口径换成可能出错的口径。

`run_metric(metric, dimensions, start, end)` 直接走编译路径：

```
run_metric(metric="aov", dimensions=["city"], start="2026-09-01", end="2026-10-01")
```

归期字段、过滤条件、join、NULL 归组全部由语义层保证，模型只负责"选哪个指标、
按什么维度分组"，编译器的 fan-out 警告也一并透出。

**实测（44 条带参考 SQL 的题）**：

| 版本 | 静默错误率 | 均 token | 均步数 |
| --- | --- | --- | --- |
| v3（模型手写 SQL） | 21~23% | 8,346 | 1.14 |
| 编译优先（首版） | 18.2% | 10,393 | 1.30 |
| **编译优先 + 检索改进 + 不变量 + 对算** | **18.6%** | **9,708** | 1.20 |

正确率更好，token 比 v3 高约 16%。**注意 ±1~2 题的运行方差**——18.2% 与 18.6%
的差别不构成差异，但两者都优于手写 SQL 的 21~23%。44 题里约 13~16 题走编译路径。

**这条路暴露了两个必须一起修的问题**——不修的话它反而更差（第一版实测静默
错误率 27.9%，比手写还烂）：

1. **维度 NULL 归组**：参考口径用 `COALESCE(city,'未知')`，而编译器原来直接输出
   `users.city`，两边的分组集合对不上（一个出现 NULL 组、一个是"未知"组）。
   修法是在 `tables.yaml` 给字段声明 `null_label`，编译器统一补 COALESCE——
   规则 R005 本来就要求"显式说明 NULL 怎么归组"。
2. **维度列名**：编译器内部用 `d0..dn` 做 CTE 对齐，直接暴露给用户既不可读、
   也让结果集比对对不上。新增 `friendly=True`：最外层输出用字段原名，
   内部对齐不动。

还有一个连带的坑：**评测脚本原来只从 `run_sql` 取 SQL**，加了 `run_metric` 之后
编译路径跑出来的题会全部漏评。现在工具调用记录统一带 `sql` 字段（`run_sql` 从
入参取、`run_metric` 从编译产物取）。

### 多路径对算：用编译器复核手写的 SQL

静默错误里最难抓的一类是"**数值自洽但口径被替换**"——例如算客单价时把分子从
GMV 悄悄换成净成交额。`agent/sanity.py` 那四项不变量抓不住它（四个等式全不破）。

`semantic/multipath.py` 补的就是这一类：**同一个指标，用编译器再算一遍，
两条独立路径对不上就报警**，报警会回灌给模型让它核对。

只在能可靠判定时触发，宁可少报也不误报：

* 结果是**单行标量**（编译对照只做标量，分组结果不做）
* 列名能对上语义层里**定义过的指标**
* SQL 里的时间区间可解析
* SQL 的过滤条件**不超出**该指标声明的过滤条件——否则本来就是另一个口径
  （例如"只算 VIP 的客单价"），对照没有意义

实测（构造用例）：净额冒充 `gmv` → 报警；客单价分子用净额 → 报警；
正确口径、只算 VIP、分组结果 → 均不报警。真实查询上零误报。

**编译路径（`run_metric`）不做这个检查**——它的 SQL 本来就是编译器产出的，
自己对自己是同义反复。

### 检索召回改进

实测确认的问题（`购买额` 命中错指标、`流水` 从未写进别名表、
`VIP成交额占比` 因为别名不连续而失配）做了三处修复：

1. **补别名**：`流水`/`购买额`/`消费额`/`退了多少单`/`卖了多少钱`/`访问用户` 等；
2. **隔字匹配**：别名中间允许插少量字（`VIP占比` 能命中 `VIP成交额占比`），
   但分数**低于精确命中**，保证精确优先；只对长度 ≥ 3 的别名启用，避免误伤；
3. **按区间判包含**：原来"被更长别名包含就让位"是按**字符串**比的，
   隔字匹配一上来就判错（`VIP成交额` 与 `VIP占比` 互不包含）。
   改成按**在问题里的命中区间**比，一次修好。

| | 召回 | 精确 | 干净命中 |
| --- | --- | --- | --- |
| 主集（改进前） | 75.0% | 70.0% | 62.5% |
| **主集（改进后）** | **85.0%** | **82.5%** | **77.5%** |
| 留出集（改进前） | 67.5% | 72.5% | 65.0% |
| **留出集（改进后）** | **97.5%** | **97.5%** | **97.5%** |

顺带修了一处规则漏召回：命中 `net_gmv` 时，`scope=gmv` 的 R002 不会被带上
（规则只匹配直接选中的指标）。现在沿指标依赖展开。

**新的门禁项**：`check_retrieval` 把"检索干净命中率"设成回归护栏（下限 55%）——
以后改别名，不会再悄悄把本来对的题弄错。

## Agent 执行循环

```
understand ──(需要澄清)──> END（返回澄清问题）
    |
    +──> act ──> observe ──(发现问题)──> reflect ──> act
                    |
                    +──(完成)──> synthesize ──> END
```

三个刻意的设计选择：

- **把"规划"折进 understand。** 为产出三行计划多花一次模型调用不划算，现在一次结构化输出里同时给意图和计划。
- **observe / reflect 不调模型。** 做的是确定性检查（结果为空、被截断），构造好提示回灌即可。
- **synthesize 不调模型。** 结论文本在 act 阶段已产出，synthesize 只负责附加"数据来源"。这样既省一次调用，也保证溯源信息不被模型改写。

### 三重死循环防护

| 手段 | 防的是什么 |
| --- | --- |
| 最大步数 | 兜底，任何情况下都会停 |
| 重复调用检测 | 同一个 `(工具, 参数)` 反复出现 |
| 无进展检测 | 参数变了但结果没变（摘要相同） |

只有最大步数的话，模型可能从第 3 步就开始空转，白烧 5 步的 token；只有重复检测的话，模型换个参数就能绕过去。

### 重试只对瞬态错误生效

`transient`（超时/限流/5xx）退避重试，`validation` / `denied` 不重试而是把错误回灌给模型。**重试下沉到单次工具调用，不在整轮对话外层包重试**——整轮重放会重复执行已经成功的写操作。

### 为什么要有 LLM 抽象层

循环逻辑（状态转移、熔断、预算）和"用哪个模型"是两件独立的事。抽象出来之后，循环可以用 `ScriptedLLM` 做确定性测试——不联网、不花 token，而且能把"模型会不会犯错"变成可控变量。

## 工具层

10 个工具，覆盖四类。**后两类是刻意加的**——没有有副作用的工具就讲不了幂等设计。

| 类别 | 工具 |
| --- | --- |
| 查询 | `list_tables` / `describe_table` / `search_metrics` / `run_sql` / **`run_metric`** |
| 计算 | `analyze_dataframe` / `run_python_sandbox` |
| 展示 | `make_chart`（手写 SVG，不依赖 matplotlib） |
| **有副作用** | `export_report` / `send_notification`（幂等） |

**错误分类**。工具不抛裸异常，而是把错误分成五类，直接决定重试策略：

| 类型 | 含义 | 策略 |
| --- | --- | --- |
| `validation` | 参数不合法、字段名写错、表名拼错 | 不重试，把错误回灌给模型让它改 |
| `denied` | 安全校验拦截 | 不重试，需要改写或人工确认 |
| `transient` | 超时、限流、连接失败 | 可退避重试 |
| `business` | 业务规则不满足 | 交给模型决策 |
| `internal` | 我们自己的 bug | 不重试，需要修 |

这里有个容易忽略的细节：**表名拼错和越权访问在语法上长得一样，但处理方式必须不同**。前者要让模型自我修正，后者必须硬拦。所以 `run_sql` 会用字符串相似度区分——`FROM orderz` 返回 `validation` 并提示"你是想写 orders 吗"，`FROM secret_payroll` 返回 `denied`。

## SQL 安全校验

这一层的设计前提是**不要相信模型生成的 SQL**。五层防护：

| 层 | 措施 |
| --- | --- |
| 语句类型 | 只允许 SELECT / UNION，拒绝 INSERT/UPDATE/DELETE/DROP/CREATE/ALTER/TRUNCATE |
| 语法结构 | 禁止多语句拼接（`SELECT 1; DROP TABLE t`）、禁止 `SELECT ... INTO` |
| **函数白名单** | 默认拒绝未知函数——`pg_read_file('/etc/passwd')` 语法上是合法 SELECT，靠语句类型判断拦不住 |
| 表白名单 | 只允许语义层里定义的表，并额外拦截 `information_schema` / `pg_catalog` / `duckdb_*` |
| 资源限制 | 自动补 `LIMIT`，防止全表扫描 |

**为什么按表达式类型而不是函数名字符串做白名单**：sqlglot 会把函数名规范化——`DATE_TRUNC` 解析成 `TimestampTrunc`、`STRFTIME` 解析成 `TimeToStr`，而所有它不认识的函数（包括 `pg_read_file` 和看起来无害的 `NOW()`）都变成 `Anonymous`。按用户写的函数名去比白名单，`DATE_TRUNC` 会被误杀。

**已知边界（不夸大）**：这一层只做静态检查，拦不住"合法函数 + 合法表"组合出的错误业务语义（比如该用净额的地方用总额）。那要靠评测体系，不是安全校验能解决的。

沙箱同理——`run_python_sandbox` 只做了很浅的限制（禁 import、白名单内置函数），**不是真正的安全边界**。真正隔离需要子进程 + 容器 + 资源限制。代码注释里写清楚了这一点。

按 **OpenTelemetry GenAI 语义规范**埋点，轨迹结构：

**导出器可插拔**：默认只挂本地 JSONL 导出器（`traces/spans.jsonl`），完全离线可用、可回放、可测试。要接 Langfuse / Collector 时传 `otlp_endpoint` 即可，埋点代码一行不改——这正是遵循 OTel 标准而不是写死某个厂商 SDK 的意义。

```bash
./.venv/bin/python scripts/show_trace.py                        # 查看轨迹
./.venv/bin/python scripts/show_trace.py --failures-only --export-failures
```

### 失败判定的取舍

这里有个容易做错的地方：**工具报错不能一律算失败**。

参数写错、安全拦截这类错误会被回灌给模型让它自己改，属于正常工作流的一部分。如果把它们也标记成 ERROR，失败率统计会被大量"正常纠错"污染，看起来像系统极不稳定。

所以只有 `transient`（超时/限流）和 `internal`（代码 bug）才把 span 标记为 ERROR，其余记成 span 事件。

**整轮的失败判定则更宽**：只要最终状态不是 `answered`（含熔断停止、需澄清、模型故障）就算失败。因为一个把模型绕进死循环、最后被熔断的任务，恰恰是最该进评测集的样本。

### 失败回流

`--export-failures` 把失败轮次导出成候选样本，**刻意不直接写进 `tasks.jsonl`**：评测任务需要人工补标准 SQL 和口径依据，没经过人工校验的自动样本只会污染评测集。

### 隐私

Span 属性里只记工具参数的**键名**（`agent.argument_keys`），不记值——值可能含敏感数据，体积也不可控。完整 prompt 默认不落盘。

## CI 门禁

```bash
python eval/gate.py                    # 离线层，不需要密钥，几秒完成
python eval/gate.py --online --sample 12   # 加上真实模型抽查
```

门禁分两层，阈值写在 `eval/thresholds.json` 里（版本化，可 review）：

| 层 | 检查项 | 门槛 |
| --- | --- | --- |
| 离线 | 评测集合法性（ID 唯一、标准 SQL 可执行、对抗样本有 rubric） | 硬性 |
| 离线 | 自检：标准 SQL 当预测 | 必须 100% |
| 离线 | 负例：典型错误答案 | 必须 0% 通过 |
| 在线 | 答案正确率（抽样） | ≥ 50% |
| 在线 | SQL 通过率 | ≥ 60% |
| 在线 | 熔断比例 | ≤ 25% |

在线层抽样会**按类别分层**（单表 / 多步 / 对抗各抽几条），
避免只抽最简单的单表任务让门禁看起来很漂亮。

### 为什么没用 DeepEval

原计划用 DeepEval，实际评估后放弃了，原因是不匹配：

DeepEval 的指标库是围绕 RAG 和开放式生成的（忠实度、答案相关性、G-Eval 等），
而本项目的评测主体是**结果集精确比对**——同一句问句、标准 SQL 的结果是确定的，
不需要 LLM 打分。硬套 DeepEval 只能是为了在简历上多一个名词。

它真正有价值的部分是"把评测写成 pytest 断言、接 CI 门禁"这个理念，
而这一点用 pytest 直接实现更轻、更快，并且**离线层完全不需要模型密钥**，
每次提交都能跑。如果以后项目里长出了 RAG 组件，DeepEval 才值得引入。

### 门禁自己也要被测

一个永远返回"通过"的门禁等于没有门禁。所以 `tests/test_eval_gate.py` 里
既有正常路径的断言，也有"异常必须被拦住"的断言（重复 ID、缺 rubric、
标准 SQL 写错等）。

其中最有价值的一条是**元测试**：逐条验证 `wrong_answers.jsonl` 里的
每个负例确实与标准答案不同。这条测试立刻就抓出了我自己的错误——
T17 我写的"错误答案"用 `COUNT(*)` 代替 `COUNT(DISTINCT order_id)`，
但那个查询跑在 `orders` 表上、主键唯一，两者结果完全相同，
这条负例等于没测。

### 踩过的坑：并列值让"自检"随机失败

加了门禁之后跑全量测试，`test_sanity_passes` 挂了——**同一条标准 SQL
和自己比都不相等**。查下来是 T35 的 `ORDER BY conversion DESC` 有并列值，
DuckDB 并行执行时并列行的顺序不稳定，而该任务开了 `order_matters`。

这个坑有两层：

1. **任务集的问题**：排序键不唯一 → 给 28 条带排序的任务全部补上唯一
   tiebreaker，并在门禁里加了「标准 SQL 跑 3 次必须完全一致」的检查。
2. **比对逻辑的问题**：按整行位置比对本身就太严——两个城市成交额相同时，
   它们在标准答案里的先后是任意的，Agent 换个顺序不代表排名错。
   改成**解析标准 SQL 的 ORDER BY 拿到排序键，然后验证「行集合一致 +
   候选按该键单调有序」**，既能容忍并列，又能抓住真正的排序错误。

这两个问题都只在并发度变化时才暴露，靠人工测几乎不可能发现。

## 数据里埋了哪些坑

这不是一份"干净"的数据集。刻意构造的口径陷阱是为了让语义层和评测集有意义：

| 陷阱 | 数据里的表现 | 不处理会怎样 |
| --- | --- | --- |
| 下单时间 ≠ 支付时间 | 2,592 笔订单跨月支付 | 用 create_time 算成交额会算错月份 |
| 未支付订单 | 8,462 笔订单 pay_time 为 NULL | 不过滤会把未成交金额算进 GMV |
| 退款是独立表 | 3,622 笔退款，多为部分退款 | 忘记扣减会把净成交额算成 GMV |
| 折扣分摊在明细 | 59,986 笔订单的明细折扣前金额 > 订单金额 | 用明细求和算 GMV 会系统性偏高 |
| 城市可能为空 | 382 个用户 city 为 NULL | 分组时凭空出现一个 NULL 组 |

## 评测体系

核心指标是**结果集精确比对**——同一个问题，标准 SQL 的结果集是确定的，所以可以直接比对，不依赖 LLM 打分。

```bash
# 用标准 SQL 自检（验证 harness 本身）
./.venv/bin/python eval/runner.py --sanity

# 用 Agent 产出的预测评测
./.venv/bin/python eval/runner.py --predictions eval/predictions/agent_v1.jsonl

# 用"典型错误答案"验证 harness 真的能抓错（应该 0/10）
./.venv/bin/python eval/runner.py --predictions eval/datasets/wrong_answers.jsonl
```

**为什么要有 `wrong_answers.jsonl`**：一个只会返回"通过"的比对器同样能让自检跑到 100%。所以必须验证它能抓住错误。这里收集了 10 个典型错误（用错归期字段、忘记扣退款、忘记减折扣、分母用错等），当前全部能被抓住。

容差按任务级配置：金额类 0.01（一分钱）、比率类 1e-4、计数类 0（完全一致）。全局默认保持严格（1e-6），避免"精确比对"被相对容差架空。

│   ├── runner.py               # 结果集口径评测执行器
│   ├── run_agent.py            # 让 Agent 跑评测集并产出预测
│   ├── judge_runner.py         # 用评委评答案正确性
│   └── report.py               # Markdown 报告
└── tests/                      # 319 项，全部离线可跑

## 服务化

```bash
python scripts/serve.py                  # http://127.0.0.1:8000
python scripts/serve.py --port 9000 --workers 4
```

| 接口 | 作用 |
| --- | --- |
| `POST /analyses` | 提交分析，返回 `task_id`（202，不阻塞） |
| `GET /analyses/{id}` | 查询状态与结果（轮询用） |
| `GET /analyses/{id}/trace` | 取这次运行的完整轨迹（树形文本 + 原始 span） |
| `GET /analyses` | 最近任务列表 |
| `GET /health` | 存活与待处理任务数 |

**为什么是异步接口。** 一次分析 5–15 秒，同步 HTTP 会超时，网关层也没法做重试。
所以提交立即返回 `task_id`，客户端轮询。

**服务化逼出来的三个真问题，都不是"包一层 HTTP"能解决的：**

| 问题 | 单进程时的表现 | 服务化后 |
| --- | --- | --- |
| 结果句柄存哪 | 内存字典够用 | 必须落盘，否则"提交任务的 worker"和"轮询的 worker"拿不到同一份数据 → 新增 `SqliteResultStore`（带 TTL，惰性清理） |
| 任务状态存哪 | 无所谓 | 必须落盘，同样是多 worker 的要求 |
| Agent 实例能共用吗 | 可以 | **不行**。实例上有 `_started_at` 这类运行期状态，多任务共用会互相污染预算判断 → 每个任务新建实例 |

**状态机是显式的**：`queued → running → succeeded / failed / stopped`。
`stopped`（熔断）单独一类而不是并进 `failed`——"预算超了被主动停下"和
"程序出错了"是两件事，混在一起排查会误判。同理 Agent 的 `clarified`
算成功：把问题交回给用户是正常结束。

**依赖可注入。** `AnalysisService` 接收的是 `agent_factory` 而不是 Agent 实例，
所以接口层测试能注入脚本化模型，毫秒级跑完整条链路（21 项测试，不联网）。

## 设计决策

| 决策 | 理由 |
| --- | --- |
| 语义层而非直接注入 DDL | 模型需要的是业务口径。它知道字段叫 `pay_time`，但不知道"统计销售额要用支付时间而不是创建时间" |
| 表和表的关系单独声明，指标里不写 join | join 是数据模型元数据，抄进每个指标里必然会有抄漏和漂移。声明一次，编译器推导 |
| 比率、差值类指标只写业务关系，SQL 由编译器生成 | 手写会出现同一个口径写好几遍、改一处漏一处；编译产物还能被自动校验 |
| 指标引用用 `{name}` 显式标注 | 拼写错误在加载时报出来，而不是变成一句跑不通的 SQL；指标名和 SQL 标识符不会互相误伤 |
| 编译 SQL 与评测集参考 SQL 交叉校验 | 语义层写错会让 Agent 系统性算错，而评测可能一起错。两份口径必须对跑 |
| 上下文按意图检索组装 | 全量注入的 token 成本实测高约 44%。注意这是**成本**取舍，不是准确率取舍——12 题对照实验里全量注入的结果集正确率并不更低 |
| 用 DuckDB 做本地数仓 | 单文件、免部署，别人 clone 后能直接复现评测结果 |
| 数据集用固定随机种子生成 | 评测结果必须可复现，否则数字没有意义 |
| 容差按任务级配置 | 金额和比率的合理误差量纲不同，统一放宽会架空"精确比对" |
| 评测平台独立于 Agent | 可以对比不同版本、不同模型，而不是只能评测当前代码 |
| 幂等键落盘到 SQLite 而不是内存字典 | 重试常发生在进程重启之后，内存字典一重启就失效 |
| 工具返回 JSON dict 而非 Pydantic 对象 | trace 埋点、评测报告、回灌给模型都要求可序列化 |
| 有副作用的工具在没有幂等存储时拒绝执行 | 宁可报错，也不赌"它不会重复" |
| 评测对象是 Agent 生成的 SQL 结果集，不是结论文字 | 自然语言没法精确比对，SQL 结果集是确定的 |
| 没有密钥时直接报错 | 悄悄退化成假模型会让人误以为跑出了真实结果 |
| 可观测性走 OTel 标准而非写死厂商 SDK | 换后端不改埋点代码，也保证离线可用 |
| 只有基础设施类错误才标记 span 失败 | 否则"正常纠错"会污染失败率统计 |
| 失败样本导出为候选而非直接进评测集 | 未经人工校验的自动样本会污染评测集 |

## 已知问题

### 能力边界

- 语义层检索是关键词/别名匹配。经"检索召回改进"后：主集干净命中 **77.5%**、留出集 **97.5%**。主要失败模式是"**命中了错的**"而非"零命中"。表仍会轻微多召回（问"成交总额"会带上 order_items，多带不影响正确性，只让上下文长约 300 字符）。更彻底的解法是向量检索或让模型参与选表，现在还没做
- **评测集里有几处指标标注与问题语义不符**（检索改进过程中发现的，这是标注问题、不是检索问题）：`T19`/`T39` 问的是"访问**次数**"、参考 SQL 是 `COUNT(*)`（数事件），但 metrics 标成了 `active_users`（数用户）；`T22`/`T31`/`T36` 问的是"件数"，标成了 `item_amount`（金额）。语义层里没有对应的"件数/事件数"指标，标注时用了最接近的那个。这几条不计入检索改进的账
- 商品维度销售额假设订单级折扣已分摊到明细，真实数仓里不一定成立
- **沙箱不是真正的安全边界**。它只禁了 import 和白名单内置函数，没有进程/容器隔离。代码注释里写明了，但**没有做过真实的逃逸测试**。生产环境必须换成子进程 + 容器 + 资源限制
- 语义层只覆盖 6 张表 / 14 个指标，且数据是合成出来的（虽然埋了 5 类真实口径陷阱）
- **编译器只能表达单一归期主体的指标**。同时受两个时间条件约束的口径（"9 月注册且 9 月完成首单支付"）表达不了，只能标出来不做交叉校验。行业里的做法是引入更完整的维度/时间角色声明，本项目没做到那一步
- **fan-out 只警告不拦截**。按商品类目给订单级指标分组时，编译器知道行数会膨胀并给出提示，但仍会生成那条 SQL。正确做法是拒绝编译并给出替代指标

### 评测方法的局限

- **结果集比对回答的是"有没有产出过形状一致的结果"**，不等于"答案对不对"。已确认两类误判：标签表示不同（布尔 vs 中文字符串）、表格形状不同（宽表 vs 长表），这两类情况下 Agent 答案是对的。所以主指标改用 LLM 评委
- **评委和选手是同一个模型**，存在自我偏好风险。严格做法应该用不同厂商的模型交叉评审
- **评委校准样本只有 6 条**，不足以支撑"评委可信"的强结论
- **熔断不等于答错**：T04 触发了步数熔断，但它在熔断前已经算出了正确结果
- 真实模型只跑了两轮、每轮 60 条，样本量不足以谈稳定性
- 半自动指标（数值列一致率）只检查数值列，标签列完全不参与

### 工程上的缺口

- 本地 JSONL 轨迹没有轮转和清理，长期运行会持续增长
- 任务表和结果表没有清理策略，只有结果句柄有 TTL
- 单进程 uvicorn 未做压测；`ThreadPoolExecutor` 的队列没有上限，突发流量会把任务堆在内存里
- 没做鉴权。任何能访问端口的人都能提交分析任务
- 还没接 Langfuse（本机 Docker 不可用；OTLP 导出器已实现，但没在真实后端验证过）
